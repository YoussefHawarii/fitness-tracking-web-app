# Nutrition-label OCR runs only in the user's browser

Reading a nutrition label from a photo is done entirely on the user's device with Tesseract.js (Arabic and English), and the backend has no endpoint that accepts a label image. The deciding requirement is privacy: the photo and the text recognised from it must never be uploaded to our backend or a third party, stored, logged, or sent to analytics — only the product values the user reviews and submits are saved. The previous design routed the photo to `POST /food/nutrition-label/extract`, a stub awaiting a server-side provider; that route, its service, and the frontend upload call are removed rather than left dormant, so no path exists that could receive an image.

Hosted vision/OCR APIs (Google Cloud Vision and similar) were rejected because they send the photo to a third party, cost money per request, and typically require a payment card; the app had already rejected paid photo-based food recognition for the same cost reasons. Server-side Tesseract was rejected because it still uploads the photo. The cost of the in-browser choice is accuracy and device load: a few megabytes of engine and language data downloaded on first use, slower recognition on low-end phones, and iPhone memory limits — which is why the engine is loaded only when the user opens label scanning, a single worker is reused for that scanning session and terminated when it ends, and the feature ships only after the physical-device validation set has passed.

## Consequences

- All OCR assets — worker, WebAssembly engine, and the `eng`/`ara` language data — are self-hosted on the frontend's own origin under versioned URLs. Tesseract.js's default CDN locations are never used, because even asset requests would tell a third party when a user scans. All engine build variants are hosted so Tesseract.js can pick the one each device supports. Language data uses Tesseract.js's default cache (IndexedDB) as upstream recommends, and the versioned assets are served with long-lived cache headers; only engine and language data are ever cached — never a photo, recognised text, or a Label reading.
- An enforced Content-Security-Policy on the frontend limits where the page can connect to, so the privacy promise is backed by the browser and not only by code review. It applies site-wide, so changes to it are verified against Google sign-in, avatar images, and the barcode scanner.
- OCR text and image data are never passed to console output, error messages, URLs, or request bodies; errors are reported generically.
- The user-facing promise is limited to what is true: the photo and its recognised text are processed on the device and never uploaded or saved, and the browser may keep the recognition engine cached. The app does not claim that nothing is stored on the device, that scanning works offline, or that readings are accurate — every reading is reviewed before it reaches the form.
