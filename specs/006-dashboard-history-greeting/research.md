# Phase 0 Research: Dashboard History Calendar & Time-Aware Greeting

No `[NEEDS CLARIFICATION]` markers remained in the spec. This document records the codebase investigation that resolved every Technical Context unknown and the design decisions it led to.

## Decision: Reuse the three existing date-parameterized read endpoints; add no new endpoints

- **Decision**: `GET /balance?date=`, `GET /exercise-logs?date=`, and `GET /food/logs?date=` (`Backend/src/modules/calorie-balance/calorie-balance.controller.ts`, `Backend/src/modules/food/food.controller.ts`) already accept an arbitrary calendar date and already return everything FR-003/FR-004 need — daily totals, exercise sessions, and itemized food entries. Today `Dashboard.tsx` only ever calls the first two, and only ever with `todayLocalDate()`.
- **Rationale**: All three endpoints are proven in production use (the food-log page already calls `listFoodLogsForDay`; the dashboard already calls the balance/exercise endpoints for "today"). Making the calendar work is primarily a matter of parameterizing the *existing* calls with a user-selected date instead of always "today", not building new read paths.
- **Alternatives considered**: A new combined "day summary" endpoint that returns food + exercise + totals in one call was considered, to reduce the Dashboard to a single request. Rejected: it would duplicate logic already correctly split across `CalorieBalanceService`/`FoodService`, and FR-008 requires the food and exercise sections to fail/retry *independently* — a single combined endpoint would make that harder, not easier.

## Decision: Persist a `name` snapshot on `FoodLogEntry` at creation time

- **Decision**: Add a `name String @default("")` column to `FoodLogEntry`, populated in `FoodService.createFoodLog` from whichever source resolved the nutrients (`match.name` for USDA, `product.name` for Open Food Facts, `localItem.name` for LOCAL — all three already carry a `name` field per `UsdaFoodMatch`, `OpenFoodFactsProduct`, and `LocalFoodItem`, confirmed in `Backend/src/modules/food/clients/*.client.ts` and `dto/create-local-food-item.dto.ts`).
- **Rationale**: `FoodLogEntry.sourceRef` is an opaque identifier per source type (a USDA `fdcId`, an OFF barcode, or a `LocalFoodItem.id`) — never a human-readable name (confirmed by reading `food.service.ts`'s `resolveNutrients`). FR-003 requires the Dashboard to show "the food items logged" on a past day; without a stored name, the history view could only show raw IDs. Snapshotting the name at log time (rather than re-resolving it at read time) is also more correct for history: a USDA record or a user's own local item can be edited/removed later, and a history view should show what the user saw the day they logged it, not what the source says today.
- **Alternatives considered**: Resolving the name at read time by re-querying USDA/OFF per entry, or joining `LocalFoodItem` for LOCAL entries. Rejected — it would require a live external API call (USDA/OFF) just to render history, adding latency and a new failure mode (SC-002's 2-second budget, FR-008's error handling) for data that doesn't change once logged; and it silently breaks if a USDA/OFF item is ever removed or renamed upstream.
- **Backfill**: The column defaults to `""` and existing rows are left as-is (never backfilled); the frontend renders a generic fallback label ("Food item") for any entry with an empty name, so no backfill migration is required. This project has no `migrations/` directory (per CLAUDE.md) — the column is added via `prisma db push` + `prisma generate`.
- **Implementation note**: at implementation time, this column (named `name`, non-nullable with a `""` default) and its `createFoodLog` capture logic were already present on disk — the original design here called for a nullable `foodName String?` instead. The plan/data-model/contracts docs were updated to match the actual `name` column post-hoc rather than renaming the already-working column; behavior (no backfill needed, fallback label for empty values) is equivalent either way.

## Decision: Expose `User.timezone` via `GET /profile`, reuse it for both the calendar's day boundary and the greeting

- **Decision**: Extend `UsersService.getProfile()` to also select and return `timezone` from the `User` record alongside the existing `UserBaseline` fields. The frontend fetches it once (a new call the Dashboard doesn't currently make) and uses it for two things: (a) computing the calendar's "today"/max-date boundary and which date string to request, and (b) computing the greeting's hour via `Intl.DateTimeFormat('en-US', { timeZone, hour: 'numeric', hour12: false }).format(new Date())` — no new date library needed, `Intl` already resolves an arbitrary IANA timezone's local hour natively.
- **Rationale**: `User.timezone` already exists and is already the source of truth the *backend* uses for day-boundary math (`day-boundary.util.ts`'s `getDayBoundaryUtc(dateStr, timezone)`, called from both `calorie-balance.service.ts` and `food.controller.ts`). The frontend currently has no way to read it at all — `Dashboard.tsx`'s `todayLocalDate()` and `greeting()` both use the browser's local `Date`, which can silently disagree with the account's stored timezone (FR-010/FR-011 exist specifically to close that gap). Reusing the same field end-to-end (rather than introducing a second timezone concept) keeps the calendar's day boundary and the greeting consistent with each other and with the balance calculation.
- **Alternatives considered**: A dedicated `GET /users/timezone` (or similar) endpoint was considered to avoid coupling the timezone to the baseline-gated `/profile` endpoint (`getProfile()` throws `404` if onboarding/baseline isn't complete). Rejected as unnecessary: the Dashboard already depends on baseline data existing (calorie balance requires TDEE, which requires baseline) via `GET /balance`, so requiring baseline for the timezone read too introduces no new precondition in practice.

## Decision: Native `<input type="date" max={todayInAccountTimezone}>` for the calendar control

- **Decision**: Use a plain HTML5 date input (wrapped in a small `HistoryDatePicker` component for the "back to today" affordance and date-indicator label), not a third-party calendar/date-picker library.
- **Rationale**: No date-picker or date-utility library (`date-fns`, `dayjs`, `luxon`) is installed in `Frontend/package.json` — every existing date computation in the codebase (`Dashboard.tsx`'s `todayLocalDate()`) hand-rolls native `Date`. Spec 005 established the precedent of preferring zero new dependencies when an existing browser/native capability suffices. `<input type="date">` natively supports a `max` attribute (satisfies FR-002 "no future dates") and needs no extra rendering code for a calendar grid.
- **Alternatives considered**: A custom-built calendar grid component, or adding a library like `react-day-picker`. Rejected for this feature's scope — a single date-selection control doesn't need a bespoke grid, and adding a new dependency for one control contradicts the project's established minimal-dependency pattern.

## Decision: Validate the `date` query parameter on all three read endpoints

- **Decision**: Add `@IsDateString()` validation (via a small shared query DTO) to `date` on `GET /balance`, `GET /exercise-logs`, and `GET /food/logs`, returning a `400` for a malformed value instead of the current silent behavior.
- **Rationale**: Today `date` is a bare `@Query('date') date: string` with no validation on any of the three endpoints (confirmed by reading `calorie-balance.controller.ts` and `food.controller.ts`) — a malformed value flows into `getDayBoundaryUtc`'s unvalidated `dateStr.split('-')`, silently producing `Invalid Date`/`NaN` rather than an error. This was low-risk while the only caller was a hardcoded, always-well-formed "today" string; this feature makes `date` user-selected input for the first time, so a malformed value (e.g. a manipulated request, or a bug in the calendar's ISO-formatting) should fail loudly per FR-008, not silently return wrong data.
- **Alternatives considered**: Leaving validation as-is and relying entirely on the frontend's `max`/native date input to guarantee well-formed values. Rejected — the frontend cannot guarantee the backend only ever receives values it produced (the API is directly callable), and silent `Invalid Date` propagation is a latent correctness bug independent of this feature's UI.
